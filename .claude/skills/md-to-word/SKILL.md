# MD → Word 工作流（写作优化 + 导出）

## 核心原则

写作优化的目标不是"看起来不像AI写的"，而是**写得更好**。降低AI痕迹是优化过程中的自然结果，不是目的本身。

三条底线，任何时候不能突破：

1. **完整性** — 原文所有关键信息、数据、论点必须保留，不因追求"人味"而删减实质内容
2. **逻辑性** — 论证链条不可断裂，段落关系不可颠倒（除非原结构本身有逻辑问题），因果关系必须清晰
3. **科学性** — 专业术语不能口语化替代，数据不能模糊化处理，引用/出处不能丢失

每条改动都必须能同时回答两个问题：
- 这样改让文章更好吗？
- 有没有破坏上面三条底线？

如果一条改动只是为了"消除AI感"但会损害完整性/逻辑性/科学性，那么**不做这条改动**。

包含以下任一关键词即启动：

## 工作流程

### Step 1：确认输入

拿到用户给的 `.md` 文件路径。如果没给，询问文件位置。

同时确认文体（影响优化强度）和任何特殊要求（"保留某部分不动"、"只要轻量润色"等）。

### Step 2：读取与分析

用 `Read` 读取 `.md` 文件全部内容。在阅读时完成诊断：

```text
□ 文体判断：学术/技术/汇报/自媒体/其他？
□ 原文AI特征密度：高/中/低（高频AI词占比、句式均匀度）
□ 原文写作质量：好/中/差（逻辑清晰度、表达准确度）
□ 完整度评估：核心论点___个，关键数据___处，引用___处
```

如果文件 > 3000 字，标记分块处理。

### Step 3：写作优化（核心）

按下面的 **优化操作库** 执行。优化强度根据文体自动匹配：

| 文体 | 强度 | 说明 |
|------|------|------|
| 学术论文 / 正式公文 | L1（轻量） | 仅做词汇优化，保留完整学术结构 |
| 技术文档 / 说明书 | L1（轻量） | 术语不动，仅优化冗余表达 |
| 工作汇报 / 周报 | L2（标准） | 词汇优化+句式调整，保留数据和结论 |
| 公众号 / 自媒体 | L3（深度） | 可做结构微调+叙事化 |
| 个人随笔 / 博客 | L3（深度） | 可做结构微调+口语化 |
| 聊天记录整理 | L4（重写） | 保留核心信息，按人的逻辑重写 |
| 默认（不确定） | L2（标准） | 词汇优化+句式调整 |

**用户可指定强度**，此时以用户指定为准。

---

#### 优化操作库

##### A. 词汇优化（所有强度级别都执行）

**A1. 精简虚词**

查找并删除以下冗余虚词（前提：删后句意不变）：

| 目标词 | 处理方式 |
|--------|----------|
| 进行 / 予以 / 加以 / 开展 | 直接删除或替换为具体动词 |
| 具有 / 存在（冗余用法） | "具有重要的意义" → "很重要" |
| 该+名词（非正式文体） | "该公司" → "这家公司"/直接使用名称 |
| 能够（冗余时） | "能够有效提升" → "能提升" |

**A2. 修饰词瘦身**

AI文本倾向于在名词前堆砌修饰词。规则：
- 拿掉修饰词后句意不变 → 删
- 拿掉后句意改变 → 保留

需删除的高频水词：深刻、充分、有效（做形容词时）、积极、全面、显著、高度、深入
需警惕（视上下文决定）：核心、关键、重要、必要、基本

例外：学术论文中，某些修饰词有实质语义（"显著差异"在统计学中有明确定义），**必须保留**。

**A3. AI高频词替换**

| AI倾向 | 推荐替换 |
|--------|----------|
| 然而 / 但是 | 不过 / 可 / 或不替换（保持语义强度） |
| 此外 / 另外 / 同时 | 还有 / 再说 / 或直接跳过 |
| 因此 / 所以 | 所以（精简） |
| 值得注意的是 | 去掉，或"其实" |
| 综上所述 | 去掉，或"总的来说" |
| 毋庸置疑 / 显而易见 | 去掉（不必强调） |
| 在...的背景下 / 随着...的发展 | 去掉，直接进入主题 |

**特别注意**：英文AI高频词也需处理 — delve, navigate, leverage, pivotal, notably, multifaceted, consequently

##### B. 句式优化

**B1. 破坏等长节奏**

AI文本的典型特征：每句长度接近（25-35字），每段句数接近（3-5句）。

优化方法（不破坏语义前提下）：
- 长句之后接短句（3-12字），形成节奏变化
- 一段可以只有一句话，也可以有6-8句
- 适当用问句、感叹句、插入语打破单调

**B2. 处理工整排比**

AI爱排比，尤其三连。但排比本身不是问题——空洞的排比才是。

处理方法：
- 排比的三项中，保留最有信息量的1-2项
- 剩余项用不同句式重组，或并入前一项
- 不要机械拆除所有排比——排比本身是合法修辞

**B3. 断句与合并**

- 过长的句子（>50字）拆成2-3个短句
- 过短的句子（<8字）群考虑合并为复合句
- 目标是节奏变化，不是全部变短

##### C. 结构微调（需谨慎 — 完整性/逻辑性检查点）

**C1. 开头优化**

问题开头模式：
- "随着/近年来/在当前背景下"式铺垫

处理：
- 直接删掉开头铺垫句，从具体内容开始
- 或者替换为一个具体问题/观察/数据

**完整性检查**：被删掉的铺垫如果包含背景信息（如政策背景、研究现状），需将信息融入后续正文。

**C2. 结尾优化**

问题结尾模式：
- "综上所述"/"总而言之" + 重复前文 + "仍需进一步探索"

处理：
- 删"综上所述"，保留实质性结论
- 如果结尾确实没有新信息，可以改为开放性提问或一句有力总结

**完整性检查**：如果原文结尾有实质性总结或未在前面出现的信息点，**必须保留**。

**C3. 段落间连接**

AI文本的连接方式：大量使用"首先/其次/最后"、"第一/第二/第三"。

处理：
- 减少显式路标词，让语义自然过渡
- 保留实际的分点结构（内容不变），只改连接词
- 不改变段落顺序（除非原顺序明显存在逻辑问题）

**逻辑性红线**：段落顺序只能调换当且仅当原文本身存在逻辑错乱，且调换后论证更清晰。不允许为"打散AI结构"而随意重排。

##### D. 注入写作质感（非必须，但推荐）

**D1. 具体化**

AI文本倾向于抽象概括。在**不歪曲原意**的前提下，把抽象表述具体化：

| 抽象 | 具体 |
|------|------|
| 远程办公降低了团队沟通效率 | 远程办公后，一个原本30分钟能过的需求，现在要拉群、等回复、约会议，拖到半天 |
| 过度使用社交媒体的心理健康影响 | 刷完两小时短视频之后的空虚感 |

**完整性/科学性检查**：具体化时不能编造数据或事例。如果无法用原文信息做具体化，保持原样。

**D2. 立场选择**（仅适用于有观点输出的文体，不适用于学术综述/技术文档）

AI文本规避立场："一方面...另一方面..."

处理：
- 如果原文内容包含明显偏向，去掉平衡表述，直接表达偏向
- 如果不是非此即彼的问题，保留复杂性，但避免"A有道理，B也有道理"式废话

**科学性红线**：学术论文中，平衡表述代表学术严谨性，**不能**简化为单一立场。

**D3. "元认知"标记**（仅L3强度使用）

偶尔加入写作过程中的"自我觉察"：
- "写到这儿突然意识到..."
- "说回正题"
- "其实核心就一点"

**注意事项**：学术论文/技术文档中不使用元认知标记。

**D4. 语气控制**（按文体调整密度）

| 文体 | 语气词密度 | 示例 |
|------|-----------|------|
| 学术论文/正式公文 | 禁止 | 无 |
| 技术文档 | 极低 | 偶尔"说白了" |
| 工作汇报 | 低 | "讲真"、"说实话" |
| 公众号/自媒体 | 中 | "吧"、"嘛"、"哈哈" |
| 个人随笔/博客 | 高 | 全放开 |

---

#### 中文AI绝杀特征处理指南

以下特征出现时**必须处理**，但处理方式必须兼顾完整性/逻辑性/科学性：

1. **连续四字格**（真抓实干、锐意进取、开拓创新）
   - 处理：保留核心含义，改为白话
   - 注意：学术术语中的四字格（如"实证研究"、"深度学习"）**不可改动**

2. **伪辩证**（"既看到机遇，也正视挑战"）
   - 处理：如果两边都言之有物，保留但换个说法；如果两边都是空话，只保留有实质内容的一边

3. **结论先行+分点论证**
   - 处理：不做结构打散，而是检查每个分点是否都有实质内容。如果没有，合并或删除空点；如果有，保持结构但降低每段内部的可预测性

4. **安全牌收尾**（"仍需进一步探索"、"还需持续关注"）
   - 处理：改为具体指出"什么不清楚"、"下一步具体做什么"

---

### Step 4：质量自检

改写完成后，逐项自检：

**完整性检查**
```
□ 原文所有核心论点是否都在？
□ 原文所有关键数据/数字是否保留且未篡改？
□ 原文引用/出处是否保留？
□ 是否有任何信息因"去AI"而被误删？
```

**逻辑性检查**
```
□ 论证链条是否完整？（前提→推理→结论）
□ 段落间因果关系是否清晰？
□ 是否有因删减导致的逻辑跳跃？
□ 每段的主题是否明确？
```

**科学性检查**
```
□ 专业术语是否被不当替换为口语？
□ 数据是否精确（没把"73.2%"改成"约七成"）？
□ 限定条件是否保留？（"在X条件下"、"从Y角度看"）
□ 是否因追求简洁而损失了表达的精确性？
```

**去AI化检查**
```
□ 删掉了所有"进行/予以/加以"类冗余虚词？
□ 开头不是"随着/近年来"式铺垫？
□ 结尾不是"综上所述"式空话？
□ 句式长度有显著变化（不是平均句长25-35字）？
□ 是否存在连续四字格或伪辩证句式？
```

**前三项检查有任一项不通过 → 不做下一步，退回修改。**

---

### Step 5：生成Word文档

改写完成后，将改写后的内容（保持markdown格式）写入临时文件：

```bash
# 写入临时文件（文件名保持原文件名+_optimized后缀）
```

然后运行转换脚本：

```bash
node md-to-word.js <临时文件> <原文件名.docx>
# 可选：指定自定义配置
node md-to-word.js <临时文件> <原文件名.docx> --config my-style.json
```

### Step 6：清理与确认

1. 删除临时文件
2. 告知用户：
   - 输出路径：`{原文件名}.docx`
   - 优化强度（L1/L2/L3）及主要改动（一句话）
   - 完整性/逻辑性/科学性自检结果（✅❌）

## 完整度损失应急处理

如果改写过程中发现无法同时满足"降低AI味"和"保持完整性"：

1. **优先保完整性** — 不为了去AI而删信息
2. **标记妥协处** — 在自检报告中标注"此处为了保留X信息，未做去AI化处理"
3. **分块策略** — 对长文本分块处理，每块独立执行质量检查

如果用户明确要求"大力去AI，牺牲一点准确性也行"→ 在自检中标记牺牲的部分，让用户知悉。

---

## 注意事项

- 不要丢失 Markdown 的原始结构信息（标题层级、列表、代码块等）
- 如果原文已经写得很好（逻辑清晰、表达准确），最多只做L1轻量润色
- 大文件（>3000字）分块处理，每块改完检查语气和风格一致性
- 用户说"不要改的地方"严格保留
- **记住：好的写作 ≈ 准确 + 清晰 + 有节奏。不是 ≈ 口语化 + 有情绪 + 看起来不像AI。**

## 配置文件 (word-config.json)

在项目目录下创建 `word-config.json` 可自定义 Word 输出格式，无需修改脚本。

**查找顺序**：`--config` 指定路径 → 当前目录 `word-config.json` → 输入文件所在目录 `word-config.json` → 使用内置默认值。

**模板文件**：`word-config.default.json` 包含所有可配置项及默认值，复制为 `word-config.json` 后按需修改。

### 常用配置示例

```json
{
  "fonts": {
    "body": "SimSun",
    "bodySize": 24,
    "heading": "SimHei"
  },
  "colors": {
    "link": "CC0000",
    "code": "006400"
  },
  "spacing": {
    "paragraphAfter": 200,
    "headingBefore": 500
  },
  "page": {
    "marginLeft": 1800,
    "marginRight": 1800
  }
}
```

### 完整配置说明

| 配置路径 | 默认值 | 说明 |
|---------|--------|------|
| `fonts.body` | `Microsoft YaHei` | 正文字体 |
| `fonts.bodySize` | `24` | 正文字号（半磅单位，24=12pt） |
| `fonts.code` | `Consolas` | 代码/行内代码字体 |
| `fonts.codeSize` | `20` | 代码字号 |
| `fonts.heading` | `Microsoft YaHei` | 标题字体 |
| `fonts.formula` | `Consolas` | 公式字体 |
| `page.marginTop/Bottom/Left/Right` | `1440` | 页边距（1/1440英寸，1440=1英寸） |
| `colors.link` | `0563C1` | 超链接颜色 |
| `colors.code` | `333333` | 代码文字颜色 |
| `colors.quote` | `666666` | 引用文字颜色 |
| `colors.body` | `333333` | 正文文字颜色 |
| `colors.tableHeaderBg` | `F2F2F2` | 表格表头背景色 |
| `spacing.paragraphAfter` | `120` | 段落后间距 |
| `spacing.headingBefore` | `360` | 一级标题前间距 |
| `spacing.headingBeforeNested` | `240` | 子标题前间距 |
| `spacing.listItemAfter` | `80` | 列表项后间距 |
| `image.maxWidth` | `500` | 图片最大宽度(px) |
| `image.maxHeight` | `700` | 图片最大高度(px) |
| `list.indentPerLevel` | `200` | 列表每级缩进增量 |
| `list.bulletChar` | `•` | 无序列表符号 |

## Markdown 元素支持对照

| 元素 | 支持情况 | 说明 |
|------|---------|------|
| **标题** #~###### | ✅ 完全支持 | 自动映射到 Word 标题样式 |
| **粗体/斜体/粗斜体** | ✅ 完全支持 | 行内混排正常 |
| **无序列表** -/*/+ | ✅ 完全支持 | 支持嵌套缩进 |
| **有序列表** 1. | ✅ 完全支持 | 自动编号 |
| **代码块** ``` | ✅ 完全支持 | Consolas 字体，缩进显示 |
| **引用** > | ✅ 完全支持 | 斜体灰色显示 |
| **分隔线** --- | ✅ 完全支持 | 居中装饰线 |
| **链接** [text](url) | ✅ 完全支持 | 可点击超链接（蓝色下划线） |
| **行内代码** `code` | ✅ 完全支持 | Consolas 字体 |
| **图片** ![alt](path) | ✅ 完全支持 | 自动获取尺寸，限制最大宽高，支持相对/绝对路径 |
| **表格** \|...\| | ✅ 完全支持 | 表头灰底，支持左/中/右对齐 |
| **行内公式** $...$ | ⚠️ 文本渲染 | 保留为 LaTeX 源码（等宽斜体），不渲染为数学符号 |
| **块级公式** $$...$$ | ⚠️ 文本渲染 | 居中显示 LaTeX 源码 |
| **网络图片** ![alt](https://...) | ⚠️ 仅文本 | 由于无法下载网络图片，显示为图片链接文本 |
| **Mermaid/Graphviz** 图表 | ❌ 不支持 | 需先在 Markdown 中转换为静态图片 |
| **HTML 标签** | ❌ 不支持 | 按原文本显示 |

> ⚠️ **公式说明**：LaTeX 公式在 Word 中渲染为等宽斜体源码而非数学符号。如需渲染公式，建议在 Markdown 中将公式用 KaTeX 或 LaTeX 编译为图片后再引用。
